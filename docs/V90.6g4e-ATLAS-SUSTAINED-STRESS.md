# V90.6g4e — sustained Atlas stress, render pacing and post-GC heap tracking

**Status: CI validated and merged into main on 2026-11-23 as PR #112 (`c19aaa0ef727e440fa3c9ab86e6f57fe7b1f4667`); deployment verification is tracked separately.** This next step follows [V90.6g4d's measured short benchmark](V90.6g4d-ATLAS-RENDER-BUDGET.md). It adds no new datasets, changes no licensing decisions and leaves production map scripts untouched.

## CI method and acceptance

- Build only the existing rights-allowlisted public Pages artifact and generate the exact source-validated WRI 2021 PMTiles archive (34,936 historical source records). Deliver vector ranges with HTTP 206. Use the independent existing GDW archive with 41,145 source barriers; keep separate ODbL layers disabled.
- Run headless Chromium with SwiftShader at **1440 / 1024 / 390 CSS px**.
- Across **six passes per viewport**, repeat **12 geographically diverse pan/zoom cameras per pass** (72 camera updates), including both sides of the 180° meridian at zoom 8. On each pass, switch WRI GPU mode off and on, require the standard fallback and then real GPU symbols to recover, and confirm GDW remains selected.
- Measure a post-forced-GC **V8 JS heap sample per pass** using Chrome DevTools Protocol and record request paths, PMTiles byte-range responses, measured requestAnimationFrame intervals and full-feature scan counters. Retain raw JSON and final screenshots as workflow artifacts.
- Enforce the known correctness invariants: one original WRI JSON load per browser session, exact source counts, no unexpected ODbL sources, no page errors or horizontal overflow, GPU feature queries bounded by a deliberately loose per-camera budget, and standard fallback that remains usable.
- Add a loose **96 MiB post-GC heap-growth alarm** relative to the second pass. This is a regression tripwire, *not* evidence that a smaller growth is leak-free; GC pressure, rendering backend and runner behavior can differ significantly. Preserve results so future releases can compare distributions rather than reporting fake speedups.
- Rerun the short V90.6g4d render test and independent GDW browser suite in the same job. Never mark this test complete from a pull request merge alone.

## Interpretation and limits

All timestamps, heap samples, frame intervals and request counts come from a **headless CI runner** with software graphics. RequestAnimationFrame intervals may include tab scheduling and network delays. Neither JS heap nor request-body totals measure GPU VRAM, whole-browser process RSS, physical-phone energy usage or real-world FPS. In particular, an observed 16.7ms headless animation frame does **not** prove 60 FPS on an actual phone.

Before declaring full V90.6g4 GPU/device readiness, repeat representative tests in Chrome/Firefox and at least one physical mobile browser/device, profile compositor paint and GPU memory with relevant browser tooling, review p95/p99 input-to-paint during pan/zoom, and perform much longer background/foreground soak tests. Optimizations must follow measured regressions and be validated against original source and inspector behavior.
